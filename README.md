# WIFI-eye

**집 안 어디에서 와이파이가 제일 잘 잡히는지** 폰으로 재서 히트맵으로 그린다.

노트북에서 서버를 켜고, 폰 브라우저로 집을 한 바퀴 돈다. 방마다 서서 지도를
탭하면 그 자리를 재고, 잰 자리들 사이를 메워 지도를 칠한다.

**폰에 앱을 안 깐다.** 웹페이지 하나다.

```
run.bat
→ 터미널에 QR 이 뜬다. 폰 카메라로 찍으면 열린다.
```

설치 과정이 없다. 전부 파이썬 표준 라이브러리라 `requirements.txt` 도
가상환경도 `pip install` 도 없다. 파이썬 3.10 이상만 있으면 된다.

윈도우가 아니면 `python survey.py` 로 바로 실행한다.

## 무엇을 재는가 — 그리고 왜 신호 세기가 아닌가

**브라우저는 신호 세기(dBm)를 못 읽는다.** 웹 표준에 그런 API 가 없다. 주변
AP 목록은 꽤 정확한 실내 위치가 되기 때문에 브라우저가 열어 줄 만한 정보가
아니고, 앞으로 생길 것 같지도 않다.

그래서 두 개를 잰다.

| | 재는 법 | 왜 |
|---|---|---|
| **지연** | 빈 응답을 15회 왕복, **중앙값** | 튀는 한 방을 버리려면 평균이 아니라 중앙값이어야 한다 |
| **속도** | 1.5초 동안 받은 바이트 | "N바이트 받는 시간"으로 재면 느린 자리에서 30초씩 서 있게 된다 |

실은 이쪽이 더 알고 싶은 값이다. 신호가 -50dBm 으로 좋아도 채널이 막혀 있으면
느리다. 궁금한 건 안테나 눈금이 아니라 **그 자리에서 인터넷이 되냐**다.

### 그래도 신호 세기를 보고 싶으면 (선택)

안드로이드 폰을 무선 디버깅으로 붙이면 컴퓨터에서 `adb` 로 읽을 수 있다.
폰에는 아무것도 안 깔린다.

1. [platform-tools](https://developer.android.com/tools/releases/platform-tools)
   를 받아 압축을 풀고 그 폴더를 PATH 에 넣는다 (설치 과정은 없다)
2. 폰: 개발자 옵션 → **무선 디버깅** 켜기 → 페어링 코드로 페어링
3. `adb pair 폰IP:포트` → `adb connect 폰IP:포트`
4. `run.bat` 을 다시 켜면 **신호** 탭이 하나 생긴다

붙었는지는 기동 로그가 말해 준다. 안 붙어도 서베이는 그대로 된다.

이걸 붙이는 값어치는 **원인을 가르는 것** 하나다.

```
속도 느림 + 신호 좋음   전파는 오는데 채널이 막혔다   → 공유기 채널을 바꾼다
속도 느림 + 신호 나쁨   전파가 안 온다                → 공유기를 옮기거나 중계기
```

이 구분이 아니면 숫자만 하나 늘 뿐이다.

## 준비 — 컴퓨터를 어디에 둘 것인가

폰은 **컴퓨터를 상대로** 잰다. 그래서 컴퓨터가 측정의 기준점이고,
**한자리에 두고 안 움직여야 한다.**

> **공유기에 랜선으로 꽂는 게 제일 좋다.**
> 둘 다 무선이면 무선 구간이 둘로 직렬이 되어서, 컴퓨터 쪽이 병목일 때
> 폰이 어디로 가든 같은 값이 나온다. 지도가 통째로 평평해진다.
>
> 랜선이 안 되면 컴퓨터를 **공유기 바로 옆에** 두는 것으로도 충분하다.

폰과 컴퓨터가 **같은 공유기**에 붙어 있어야 한다. 폰이 LTE/5G 로 빠져 있으면
바깥으로 한 바퀴 돌아 들어와서, 재는 게 집 와이파이가 아니라 통신사 회선이 된다.

**핫스팟은 안 된다.** AP 가 주머니에 들어가는 물건이면 폰과 AP 사이 거리가
안 변해서 지도가 노이즈가 된다.

### 폰에서 페이지가 안 열리면

기동 로그에 접속한 기기가 한 줄씩 찍힌다. 그 줄이 뜨는지부터 본다.

```
접속 — 192.168.0.42     네트워크는 통했다. 문제는 다른 데 있다
(아무것도 안 뜸)         패킷이 여기까지 오지도 못했다
```

아무것도 안 뜨면 둘 중 하나다.

- **폰이 다른 네트워크에 있다.** 제일 흔하다. 폰 와이파이 설정을 확인한다.
- **방화벽.** 윈도우에서 관리자 권한 PowerShell 로 한 번만:

```powershell
New-NetFirewallRule -DisplayName "WIFI-eye" -Direction Inbound -LocalPort 5010 -Protocol TCP -Action Allow
```

서버를 처음 켤 때 윈도우가 "액세스 허용" 창을 띄우면 **개인 네트워크**를
체크하고 허용해도 된다. 그러면 위 명령은 필요 없다.

## 도는 법

1. **평면도** 로 집 구조를 올린다. 사진도 되고, 없으면 **그리기** 로 손가락으로
   방 윤곽을 슥슥 그리면 된다. 정확할 필요 없다 — 나중에 "아 여기가 안방"만
   알아보면 된다.
2. 방으로 걸어가서 **그 자리에 해당하는 지점을 탭한다.**
3. 3초쯤 기다린다. 점에 값이 채워지고 색이 칠해진다.
4. 다음 방으로. 방마다 2~3군데씩, 집 한 채면 10~20 지점이면 충분하다.

이미 찍은 점을 다시 탭하면 그 자리를 다시 잰다. 값이 이상하게 나왔을 때 쓴다.

측정은 지점당 약 2.5초다. 빠른 자리든 느린 자리든 같다 — 그게 "정해진 시간
동안 받은 바이트"로 재는 이유다. 집 한 바퀴에 걸리는 시간을 미리 계산할 수 있다.

### 위치는 왜 손으로 찍나

폰은 자기가 집 안 어디에 있는지 모른다.

- GPS 는 실내에서 무의미하다
- 걸음수 + 나침반 추측항법은 몇 걸음 만에 어긋나고, 실내 나침반은 철근과
  가전 때문에 엉망이다

상용 도구(Ekahau, NetSpot)도 평면도에 손으로 찍는다. 이게 정석이다.

## 지도를 어떻게 읽나

**진할수록 좋다.** 어느 탭이든 그렇다 — 지연 탭에서는 값이 작을수록 좋으니
색의 방향이 뒤집히는데, 그러면 탭을 바꿀 때마다 지도를 다시 읽어야 해서
색은 항상 "좋음 = 진함"으로 고정했다.

**안 재 본 곳은 아예 안 칠한다.** 가장 가까운 측정점에서 멀어지면 색이 사라진다.
보간이 그 바깥까지 메우게 두면 재 본 적 없는 자리에 측정값과 똑같이 생긴 색이
칠해지는데, 화면에서는 둘이 구분되지 않는다. 모르는 건 모르는 걸로 남겨야 한다.

색이 옅은 것(약함)과 색이 없는 것(안 잼)이 헷갈리지 않도록, 가장 약한 자리도
배경 대비 2:1 을 넘는 단계에서 시작한다.

**색은 로그 눈금이다.** 속도를 선형으로 칠하면 낮은 쪽이 전부 뭉개진다. 집
안의 속도 분포는 공유기 옆 90, 끝방 7 하는 식으로 심하게 치우쳐 있어서, 7 과
31 이 거의 같은 색이 되어 버린다. 4배 차이인데. 그런데 하필 그 구간이 제일
중요하다 — 90 과 85 의 차이는 아무 의미가 없고(둘 다 잘 된다), 7 과 31 이
영상이 끊기냐 아니냐를 가른다.

색상은 **단일 색상 밝기 단계**를 쓴다. 무지개(색상환을 값에 매핑)를 안 쓴 이유는
색상환에 순서가 없어서다 — 초록이 노랑보다 큰지는 배워야 아는 것이고, 경계가
어디인지는 아무도 못 읽는다. 밝기는 배울 필요가 없다. 빨강↔초록도 안 쓴다.
남성 20명 중 1명이 그 축을 못 읽는다.

숫자는 점마다 직접 찍힌다. 점이 몰려서 이름표가 겹치면 값이 좋은 쪽부터
자리를 차지한다. **표** 버튼을 누르면 전부 숫자로 볼 수 있다.

## QR 은 왜 직접 짰나

`qrcode` 나 `segno` 를 쓰면 열 줄이면 된다. 그런데 이 도구는 받아서 바로
돌아가는 게 값어치라, QR 하나 때문에 pip 설치를 붙이면 "주소 치기 귀찮다"를
"파이썬 패키지부터 깔아라"로 바꾸는 것이 된다. 편해지려고 넣은 기능이 진입
장벽이 되면 안 넣느니만 못하다.

인터넷 QR API 도 안 쓴다. 집 내부 IP 를 남의 서버로 보내는 일이고, 하필
와이파이가 시원찮을 때 쓰는 도구가 인터넷을 요구하면 곤란하다.

그래서 `qr.py` 에 ISO/IEC 18004 을 직접 구현했다. 바이트 모드, 오류정정 M,
버전 1~10(최대 213바이트). 잘못된 QR 은 없는 것보다 나쁘므로 — 안 읽히면
그나마 낫고 엉뚱한 주소로 읽히면 최악이다 — 두 방향으로 검증했다.

- 레퍼런스 구현(segno)과 **모듈 행렬이 비트 단위로 같은지** 전 버전 600건
- 독립 디코더(OpenCV)로 **다시 읽어서 원문이 나오는지**, 실사용 주소 450개

그 과정에서 규격을 잘못 읽은 곳 셋을 잡았다. 셋 다 "그럴듯한 QR 이 나오지만
스캐너가 못 읽는" 종류라, 눈으로는 절대 못 찾는 것들이다.

| 무엇 | 증상 |
|---|---|
| 마스크 평가에서 여백(quiet zone)을 안 셌다 | 가장자리에 걸친 무늬를 못 봐서 위치 검출 패턴을 닮은 마스크가 뽑혔다 |
| 마스크를 고르기 **전에** 형식 정보를 넣었다 | 마스크 자신의 형식 비트가 자기 점수를 바꾸는 순환 |
| '항상 검은 모듈'을 평가 전에 찍었다 | 그 한 칸 때문에 다른 마스크가 뽑혔다 |

세 번째는 규격상 그 모듈이 형식 정보에 딸린 것(7.9.1)이라 그렇다.

터미널에는 반칸 문자(`▀`)로 그린다. 한 모듈을 한 글자로 그리면 콘솔 글자
비율(대략 1:2) 때문에 QR 이 세로로 두 배 늘어나고, 늘어난 QR 은 규격상
읽히긴 해도 카메라가 훨씬 까다로워진다. 배경색은 ANSI 로 못 박는다 — 색을
안 주면 밝은 터미널에서는 제대로, 어두운 터미널에서는 흑백이 뒤집혀 나오는데
반전된 QR 은 읽는 스캐너도 있고 아닌 스캐너도 있다. 출력이 콘솔이 아니면
(파이프, 리다이렉트) QR 을 아예 안 찍고 주소만 적는다.

`qr.py` 는 이 도구와 아무 관계가 없다. 단독으로 갖다 써도 된다.

```
python qr.py "https://example.com"
```

## 구조

```
survey.py      HTTP 서버 — 측정 상대편이자 저장소
config.py      측정·보간 튜닝 값 전부
probe.py       adb 로 신호 세기 읽기 (선택. 없으면 조용히 넘어간다)
qr.py          QR 인코더 (ISO/IEC 18004). 의존성 없음
web/survey.html  폰에서 여는 화면. 측정도 그리기도 여기서 한다
run.bat
```

경계가 하나 있다. **파이썬은 재는 상대만, 브라우저는 재고 그리기만.**
파이썬은 "지금 몇 Mbps 인지"를 모른다 — 바이트를 밀어 넣을 뿐이고, 시간을
재고 나누는 건 전부 폰이다. 그래야 재는 쪽과 재어지는 쪽이 안 섞인다.

측정 파라미터는 `config.py` 에만 있고 `/api/config` 로 폰에 넘어간다.
HTML 에 같은 숫자를 복사해 두면 값을 바꿔도 아무 일이 안 일어나는 상황이
생기는데, 그 증상은 '튜닝이 안 먹는다'로 나타나서 원인을 찾기가 유난히 어렵다.

### 연동 규격 — HTTP `5010`

| | | |
|---|---|---|
| `GET /` | | 페이지 |
| `GET /api/config` | | 측정 파라미터 |
| `GET /api/ping` | 1바이트 | 왕복시간용. keep-alive 로 재사용된다 |
| `GET /api/blob` | 끊길 때까지 | 속도용. 클라이언트가 1.5초 뒤에 끊는다 |
| `GET /api/rssi` | | adb 결과. 없으면 `{available:false}` |
| `GET`·`POST /api/points` | | 측정 결과 저장·복원 |

`/api/blob` 은 Content-Length 를 안 보낸다. 몇 바이트를 보낼지 **서버가 모르기
때문이다** — 끝내는 시점을 정하는 건 클라이언트다. HTTP/1.1 에서
`Connection: close` 면 본문은 EOF 까지고, 그게 정확히 이 상황이다.

측정 결과는 `survey_data.json` 과 폰 localStorage 양쪽에 남는다. 신호가 아예
없는 구석을 재러 갔을 때 서버 저장이 실패하는 건 정상이라, 폰에만 남아도
잃지 않게 두 군데에 쓴다.

## 튜닝 포인트

전부 `config.py` 에 있다.

| 값 | 효과 |
|---|---|
| `ping_count` | 지연 표본 수. 늘리면 안정되고 느려진다 |
| `speed_window_s` | 지점당 측정 시간. 줄이면 빨리 돌고 값이 튄다 |
| `speed_rampup_s` | 버리는 앞부분. TCP 슬로우 스타트 구간 |
| `idw_radius_frac` | 한 점이 색칠하는 범위. 줄이면 점 주변만 칠해진다 |
| `idw_power` | 보간의 날카로움. 올리면 점 근처 값이 더 강하게 남는다 |
| `heatmap_cell_px` | 히트맵 격자. 올리면 폰에서 가벼워지고 거칠어진다 |

## 한계

**이건 전파 지도가 아니라 링크 지도다.** 폰이 컴퓨터에게서 얼마나 빨리 받느냐를
재는 것이고, 거기에는 와이파이 구간 말고도 컴퓨터의 처지와 그 순간 집에서
누가 뭘 받고 있는지가 섞인다. 그래서 컴퓨터를 고정하라는 것이고, 값이
이상하면 그 지점을 다시 눌러 한 번 더 재라는 것이다.

**층을 못 다룬다.** 2층집이면 층마다 따로 서베이해야 한다. 히트맵은 평면 하나다.

**절대 기준이 없다.** 색은 항상 "잰 것들 중에서" 상대적이다. 집 전체가 다
느려도 제일 나은 자리는 진하게 칠해진다. 절대값은 숫자로 봐야 한다 — 그래서
숫자를 점마다 찍고 표를 따로 둔다.

측정 지점이 적으면 보간이 실제보다 부드럽게 나온다. 벽 하나를 사이에 두고
속도가 절벽처럼 떨어지는 게 실제인데, IDW 는 그 절벽을 모르고 완만한 경사로
